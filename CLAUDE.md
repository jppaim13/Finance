# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A personal/family finance PWA (single page, in Portuguese). There is no build system and no package manager — it's a static site you open directly in a browser or serve as-is. There is a minimal no-framework test page (`tests.html`) covering the pure date/saldo functions.

- `index.html` — the application shell: HTML + CSS + JS (~5200 lines). Uses Chart.js and the Supabase JS SDK, both loaded from CDN `<script>` tags. No framework, no bundler, no build step.
- `date-utils.js` — a handful of **pure** functions (`parseData`, `formatarData`, `calcularDataVencimento`, `mesNomeToAnoMes`, `getVencimentoIdx`, `getInstVencIdx`, `calcularSaldo`) extracted out of `index.html` specifically so `tests.html` can exercise the real production code instead of a duplicated copy. Loaded via `<script src="date-utils.js">` before the main inline script in `index.html`; also loaded standalone by `tests.html`. This is the one deliberate exception to "single file" — see Decisões.
- `tests.html` — open directly in a browser; renders pass/fail for each assertion, no server or build needed. Covers the two bug classes most likely to fail silently (date parsing/formatting, and card competência/vencimento math) plus a fixed `calcularSaldo` fixture.
- `supabase-schema.sql` — the (only) backend: Postgres schema for Supabase.
- `migrations/` — numbered, manually-applied SQL migrations for schema/RLS changes (e.g. `001_auth_rls.sql` + matching `..._rollback.sql`). These are **not** part of the normal auto-push flow — see "Schema/RLS changes" below.
- `supabase/functions/pluggy-sync/index.ts` — Deno Edge Function (Pluggy Fase 1 sync). Deployed separately (`supabase functions deploy pluggy-sync`), not part of the static site — see "Pluggy sync" under Architecture.
- `manifest.json`, `sw.js`, `icon*` — PWA shell (installable, offline app-shell caching). `sw.js` treats **both** `index.html` and `date-utils.js` as network-first, so app updates to either are picked up together on next load without needing cache-busting — see Decisões for why both, not just `index.html`.
- `README.md` — end-user setup guide (creating the Supabase project, running the schema + migrations, configuring Auth, hosting via GitHub Pages, installing as a home-screen app).

There used to be a Google Apps Script legacy backend (`apps-script.gs`) as an alternative to Supabase. It was deleted once the Fase 0 auth gate made it permanently unreachable (`showLoginScreen()` always requires a Supabase client + session before `#appRoot` becomes visible — there was no code path into the app that didn't go through it, and `index.html` had zero remaining references to it). Recoverable at the git tag `legacy-apps-script` if ever needed again — see Decisões.

## Commands

Nothing to build or lint. To work on the app, open `index.html` directly in a browser (Chrome recommended). To run the test suite, open `tests.html` directly in a browser — it's self-contained, no server needed. The only "backend" during local dev is whatever Supabase project the user configures via the in-app Settings/login screen (URL + anon key), which is stored in `localStorage` — never hardcode credentials into the file.

### Schema/RLS changes — different rules than code changes

Code changes to `index.html`/`date-utils.js`/etc. get committed and pushed automatically. Changes that touch the Supabase schema or RLS policies do **not** follow that flow:
1. Export a fresh backup first (Configurações → Backup → "Exportar tudo (JSON)").
2. Write the change as a new numbered file in `migrations/` plus a matching `_rollback.sql`.
3. The migration is applied **manually** by the user in the Supabase SQL Editor, announced explicitly — never bundled into an unrelated commit, never applied by Claude directly. This is not a technical limitation (`supabase db query --linked` does work in-session, and is used freely for read-only investigation/diagnostics) — it's deliberate: schema/RLS changes are much harder to walk back than a code revert, so the one manual step stays as a forced checkpoint the user sees before it takes effect, rather than something that already happened by the time it's mentioned.
4. One structural change at a time, each verified independently before moving to the next.

## Architecture

### Backend

**Supabase** is the only backend: the client (`_sb`, created by `conectarSupabase()`) talks directly to Postgres tables via `sbSelect`/`sbInsert`/`sbUpdate`/`sbDelete` helpers — thin wrappers around `supabase-js`. (A Google Sheets/Apps Script backend used to exist as an alternative; see the file list above for why it was removed.)

Row Level Security is **enabled** (`migrations/001_auth_rls.sql`) with a single permissive policy per table (`for all to authenticated using (true) with check (true)`) — any logged-in user (the two family members) has full read/write access; anyone without a session gets empty results. Public signup is disabled in Supabase Auth; the two users were created manually. See "Auth" below.

### Data model (Supabase tables)

- `contas` — bank accounts AND "caixinhas" (savings/investment pockets) in one table, distinguished by `tipo IN ('conta','caixinha')`. Balance is **not stored** — it's computed client-side (see below).
- `cartoes` — credit cards, linked to a debiting account via `conta_nome` (must exactly match a `contas.nome`; there is no FK, matching is plain string equality).
- `extrato` — one-off transactions. Has **two separate** linkage columns: `conta_nome` and `cartao_nome`, mutually exclusive based on `origem` ('conta' | 'cartao') — **except** rows with `categoria = 'fatura'` (fatura payments), which use both simultaneously (see below). Any code that writes to this table must preserve this convention or transactions become silently orphaned (unmatched by any account/card in the UI).
- `lancamentos` — recurring/fixed/parcelado/receita entries. Unlike `extrato`, this table has a **single** `conta_nome` column that holds either an account name or a card name depending on `origem` — do not try to split it into two fields.
- `transferencias` — transfers between `contas`/`caixinhas`.
- `repasses` — expense-splitting with spouse; fully isolated bookkeeping, does not affect account balances.
- `categorias` — user-defined categories (merged with hardcoded `CATS_DESPESA`/`CATS_RECEITA` in JS).

### Fatura (credit card bill) payment flow

Card purchases (`extrato.origem = 'cartao'`) accumulate against the card only — `conta_nome` is left blank so they never touch any account's balance. When the user pays a bill via "Pagar Fatura", a single aggregate `extrato` row is inserted with `categoria: 'fatura'`, `origem: 'conta'`, `conta_nome` = the linked account, and `cartao_nome` = the card — this is what actually debits the account. This avoids double-counting the same spend once as a purchase and again as a payment. Category/repasse aggregations explicitly exclude `categoria === 'fatura'` for the same reason.

The fatura payment's `data` field is set to the card's computed **vencimento (due) date** for that billing cycle (not "today"), so it lands in the correct month in the Extrato regardless of when the user actually clicks pay.

Once a fatura is marked paid (`state.faturasPagas`, keyed `"<cartão>-<mêsAbrev>"`), that status is **not** revalidated against the current total if purchases are later added/moved into that billing period — deliberately, since re-showing "Pagar Fatura" would charge the *full current total* again, double-debiting the account for the part already paid. Any future fix here needs to account for partial/delta payments, not just a paid/unpaid boolean.

### Auth

`iniciarAuthGate()` subscribes to `_sb.auth.onAuthStateChange` once a Supabase client exists; it's the single source of truth for whether `#appRoot` (the whole app) or `#loginScreen` is visible — `loadData()` is never called without an active session. The login screen itself has two sub-forms toggled by whether `_sb` exists yet: `#loginConnectForm` (URL + anon key — first-time setup / no `localStorage`, e.g. a fresh browser or private tab) and `#loginAuthForm` (email + password). `conectarSupabase(url, key)` is the shared helper behind both `saveConfig()` (Configurações page) and `conectarESeguir()` (login screen) — don't duplicate the connection-test logic. Logout is `fazerLogout()` → `_sb.auth.signOut()`, which the same `onAuthStateChange` callback reacts to.

### Client-side state and rendering

Everything lives in a single global `state` object, rebuilt by `loadData()` on every month change / mutation:
- `calcularSaldo(conta, ...)` (in `date-utils.js`) computes an account's balance by summing all matching `lancamentos`/`extrato`/`transferencias` rows by **exact string match** on account name (no IDs) — case, accents, and whitespace all matter.
- `montarLancamentosMes()` flattens raw Supabase rows into the shape the UI actually renders (`state.lancamentos`) for the currently selected month. It spreads the raw row first (`{...tx, ...derived fields}`) specifically so a new/overlooked column is never silently dropped — derived/renamed fields (`valor`, `contaCartao`, `cartaoNome`, `dataObj`, `mes`, `fonte`) are listed *after* the spread and must stay after it if this function is touched again, or they'd be shadowed by the raw column of the same name.
- `calcularResumo()` produces the 12-month rollup used by charts/dashboard.
- Page routing is a single registry: `const PAGES = { dashboard: renderDashboard, extrato: renderExtrato, ... }`. `navigate(page)` calls `PAGES[page]()` when switching pages; `renderAtual()` (`PAGES[paginaAtiva()]?.()`) is called at the end of `loadData()` to refresh whatever page is currently visible. **A new page = one line in `PAGES`** — there is no second list to remember to update. (This replaced a pair of hand-maintained lists that used to drift out of sync with each other, which is exactly how the Extrato page once stopped refreshing after edits.)
- The lançamento edit modal is shared across contexts (Extrato page, Faturas page item list) and branches internally on `_editingTx.fonte` (`'extrato'` vs `'transferencias'`) and `_editingTx.categoria` (`'fatura'` gets an extra card-selector field) to decide which table/columns to update. Recurring/parcelado entries (`fonte: 'lancamentos'`) use a *separate* modal/flow (`abrirEditFixo`/`executarEditFixo`), not this one.
- `#modalLancamento` (and other modals) live outside every `.page` container in the DOM — re-rendering the active page's content never touches an open modal. Rely on this rather than adding guards against `renderAtual()` when opening new modals.

### Pluggy sync (Fase 1 — espelho somente-leitura)

`supabase/functions/pluggy-sync/index.ts` (Deno Edge Function, deployed separately from the static site) pulls accounts/transactions from the Pluggy API into 5 mirror tables (`pluggy_apps`, `pluggy_items`, `pluggy_contas`, `pluggy_transacoes`, `pluggy_sync_log` — schema in `migrations/002_pluggy_espelho.sql`). It authenticates the caller via the same Supabase session used by the app (`Authorization: Bearer <access_token>`), but writes using the service role key. **It never writes to `extrato`/`lancamentos`/`transferencias`/`contas`/`cartoes`** — this phase is read-only reconciliation, not sync-to-production.

The "Sincronização" page (`renderSincronizacao`/`sincronizarPluggy`/`carregarPluggyContas`/`atualizarMapeamentoPluggy` in `index.html`) calls the function, then reads `pluggy_contas` directly (subject to the same RLS as everything else) and shows saldo real (Pluggy) vs. saldo calculado (app) per account/card, with a dropdown to map each Pluggy account to a `contas`/`caixinhas`/`cartoes` name — that mapping (`conta_nome`/`cartao_nome`/`ignorar` columns) is written straight from the browser, everything else in `pluggy_contas` only from the sync function.

**Debugging `pluggy_transacoes`/`pluggy_contas` in chat: aggregate queries only, never raw rows.** `pluggy_transacoes.descricao` routinely contains real counterparty names (transfer recipients, merchants) and `valor`/`saldo` are real money amounts — this data should never be pasted into a Claude conversation as raw `select *`-style rows. When verifying the date-timezone heuristic or the credit-card sign convention (see Decisões below), write queries that return **counts/booleans per bank**, not individual transactions — e.g. `count(*) filter (where ...)` for mismatches, not the mismatching rows themselves. This is a standing instruction, not a one-off for this session.

## Decisões

Registro de escolhas não óbvias a partir do código — principalmente as que foram cogitadas e rejeitadas, pra não serem re-tentadas sem o contexto do porquê. Agrupado por tema (era cronológico; a ordem cronológica foi o que deixou duas versões contraditórias da mesma decisão — a do diff de cartão da Pluggy — em pontas opostas do arquivo sem ninguém notar).

### Fase 0 — Auth/RLS

- **Implementado em ordem estrita, não tudo de uma vez.** Sequência: (1) botão de export/backup primeiro — é o rollback manual de tudo que vem depois; (2) cadastro público desligado + os 2 usuários criados manualmente no Supabase Auth *antes* de qualquer código de login, porque a policy do RLS libera tudo pra qualquer `authenticated`, e cadastro aberto = qualquer um vira `authenticated`; (3) tela de login construída e testada com RLS **ainda desligada**, validando o fluxo de auth sem risco de derrubar o acesso; (4) só então a migration de RLS. Motivo: religar RLS antes do login existir (ou antes do cadastro público estar fechado) transforma engano de sequência em "app mostra R$0,00 pra todo mundo" sem erro nenhum no console.
  **Bug descoberto durante a Fase 0.5 (e corrigido):** o gate de login só ativava se já existisse URL/chave do Supabase salva em `localStorage`. Numa aba anônima (storage vazio) o app caía no fluxo antigo "não configurado" e mostrava a casca inteira do app (sidebar, dashboard zerado) sem nunca pedir login — risco baixo na prática (nenhuma query real roda sem cliente Supabase), mas inconsistente. Corrigido unificando as duas telas: `showLoginScreen()` agora sempre aparece antes do app, alternando entre sub-formulário de conexão (sem `_sb`) e de login (com `_sb`, sem sessão).

### Datas e fuso horário

- **`calcularDataVencimento()` trava no último dia válido do mês — bug real encontrado ao escrever os testes.** `renderFaturas()` calculava a data de vencimento com `new Date(ano, mes, cartao.vencimento)` sem checar se aquele dia existe no mês — um cartão com vencimento dia 31 numa fatura de fevereiro estourava pra março (JS normaliza dia inválido silenciosamente). Corrigido reaproveitando o padrão de clamp (`Math.min(dia, últimoDiaDoMes)`) que já existia em outro lugar do código (`montarLancamentosMes`) mas não tinha sido aplicado aqui.

- **Lado da escrita de datas (`.toISOString().split('T')[0]`) corrigido — era o mesmo bug do `parseData`, só que na gravação.** `new Date().toISOString()` converte pra UTC antes de cortar a hora fora; em GMT-3, qualquer chamada depois de ~21h grava o dia seguinte. Trocado por `formatarData(new Date())` nos 4 pontos que gravam dado de verdade (o de maior risco: `salvarAjusteSaldo()`, que grava direto no `extrato`) e nos 3 que só pré-preenchem campo visível do formulário. Quatro outras ocorrências do mesmo padrão eram *fallback* de valor vazio que nunca dispara na prática (`extrato.data`/`transferencias.data` são `NOT NULL`, e cada call site já garante o valor antes) — removidas em vez de "corrigidas", pra não deixar código morto por trás de um comentário de bug.

- **Heurística de fuso pra datas de transação da Pluggy (`paraDataLocal()`) — CONFIRMADA nos 5 conectores (0 divergências em 1.858 transações).** A Pluggy devolve todo `date` em ISO8601 UTC. Transações vêm frequentemente como `"...T00:00:00.000Z"` (ou, no caso do Nubank, `"...T03:00:00.000Z"` — meia-noite GMT-3 já expressa em UTC), que é um MARCADOR DE DIA (a Pluggy não sabe a hora real), não um instante — converter isso pra GMT-3 sem cuidado daria o dia anterior, reintroduzindo o mesmo off-by-one do `parseData`. Regra: hora exatamente `00:00:00.000Z` → usa o `YYYY-MM-DD` cru; qualquer outra hora → é instante real, convertido pra horário de Brasília via `Intl.DateTimeFormat` com timezone **nomeada** (`America/Sao_Paulo`), não um deslocamento fixo de `-3h` — o Brasil não tem horário de verão desde 2019, então hoje dão o mesmo resultado, mas um `-3h` fixo quebraria silenciosamente (transação no dia errado, alguns meses por ano) se o horário de verão voltar; a timezone nomeada segue a regra vigente automaticamente. Verificado nos 5 bancos comparando `data` contra `(data_utc at time zone 'America/Sao_Paulo')::date` — zero divergências. `data_utc` continua guardando o valor original intocado, então dá pra recalcular `data` sem re-sincronizar se um conector novo fugir do padrão.

### Arquitetura (single-file, cache)

- **`date-utils.js` extraído do `index.html` — única exceção deliberada ao "single file".** Contém só funções puras (sem `state`, sem DOM): `parseData`, `formatarData`, `calcularDataVencimento`, `mesNomeToAnoMes`, `getVencimentoIdx`, `getInstVencIdx`, `calcularSaldo`. Motivo: sem isso, `tests.html` testaria uma cópia colada do código, que diverge da versão real em produção sem avisar ninguém. É uma extração cirúrgica de funções que já eram puras e isoladas, sem tocar o resto da arquitetura — **não** é o primeiro passo de "unificar `extrato`+`lancamentos` numa tabela `transacoes`", que segue adiada de propósito: toca todas as telas de uma vez e ainda não há rede de segurança suficiente (mais testes, mais uso da Fase 1 da Pluggy) pra fazer com confiança.

- **`date-utils.js` é network-first no Service Worker, igual `index.html` — REJEITADA a alternativa de versionar via query string (`?v=N`).** Primeira tentativa foi `<script src="date-utils.js?v=N">` com bump manual sincronizado em `SHELL` (`sw.js`). Funcionava, mas dependia de lembrar de bumpar dois lugares toda vez que o conteúdo de `date-utils.js` mudasse — esquecer não gera erro nenhum, só sintoma de saldo/data errados. Trocado por deixar o próprio Service Worker tratar `date-utils.js` como network-first, o que elimina a classe inteira do problema em vez de exigir disciplina pra evitá-la. `date-utils.js` saiu do precache `SHELL`.

### Fatura de cartão

- **Fatura "paga" revalidada contra o total atual (booleano) — REJEITADA.** Uma versão do fix fazia a fatura voltar a "pendente" se o total mudasse depois de marcada como paga (ex: compra movida/adicionada pra aquele cartão+mês). Revertida a pedido do usuário: o botão "Pagar Fatura" reaparecia cobrando o **total atual inteiro**, não a diferença — risco real de pagamento duplicado sobre o que já tinha sido debitado da conta. Não reintroduzir essa forma específica (comparar `state.faturasPagas[key]` booleano contra o total recalculado).
  **Direção aceita para o mesmo problema, ainda não implementada:** tabela `pagamentos_fatura (cartao_id, conta_id, competencia, valor, data)` — cada pagamento fica registrado individualmente, e o status/falta é derivado por `total − soma(pagamentos)` em vez de um booleano único. Isso permite pagamento parcial e recompra depois de pago sem duplicar cobrança. **Migration independente** (`00N_pagamentos_fatura.sql`), não bloqueada por nenhuma fase — pode ser feita a qualquer momento. O ponto de atenção real é migrar os pagamentos já existentes (linhas de `extrato` com `categoria='fatura'`) para a tabela nova antes de trocar a leitura, não uma dependência de fase.

### Segurança e infraestrutura

- **Visibilidade do repositório (público/privado) é uma decisão separada de Auth/RLS.** Repo público hoje não é risco de segurança por si só (nenhum segredo commitado — URL/chave do Supabase ficam em `localStorage`, nunca no código). O risco real de exposição de dados é a ausência de autenticação/RLS no banco. Se só uma dessas duas puder ser endereçada primeiro, priorizar Auth/RLS — tornar o repo privado sem RLS não protege os dados financeiros, só esconde o código-fonte.

### Legado

- **`apps-script.gs` removido do repositório, junto com o banner de "configure sua planilha" em `index.html` e o README reescrito.** Motivo: o gate de login da Fase 0 exige cliente Supabase + sessão antes de mostrar `#appRoot`, então o caminho Apps Script ficou permanentemente inalcançável — `grep -n "doGet\|doPost\|script.google\|action="` em `index.html` não retornou nada. Manter um arquivo morto no topo da árvore é convite pra uma sessão futura tentar "preservar compatibilidade" com um caminho que não existe. Recuperável por completo na tag git `legacy-apps-script`. O README foi reescrito do zero pro fluxo real (Supabase + Auth), não só editado, porque o documento inteiro era sobre o setup do Apps Script.

### Pluggy — Fase 1 (mecânica e API)

- **Sem endpoint de listagem de items — `pluggy_items` existe só por causa disso.** A API da Pluggy não expõe uma forma de listar os items (conexões banco↔Pluggy) já criados por "razões de segurança" deles; cada `itemId` precisa ser copiado manualmente do Dashboard e cadastrado. `pluggy_items(app_id, pluggy_item_id, banco)` é essa lista manual — sem ela, `pluggy-sync` não sabe quais bancos consultar e sincroniza silenciosamente zero contas.

- **`/transactions` da Pluggy foi descontinuado (HTTP 410); `/v2/transactions` tem duas armadilhas a mais — as três só apareceram testando com os 5 bancos reais.** (1) O endpoint certo é `GET /v2/transactions`, parâmetro de data `dateFrom` (não `from`). (2) `pageSize` não é aceito no v2 (`400 "property pageSize should not exist"`) — tamanho de página parece fixo (500) do lado da Pluggy agora; removido da URL. (3) **O campo `next` da resposta é inconsistente entre conectores**: no Nubank veio como URL absoluta; em pelo menos um dos outros (XP/Mercado Pago/Inter) veio só como fragmento de query (`?accountId=...&after=...`), quebrando com `TypeError: Invalid URL` ao usar direto. Corrigido com `new URL(next, \`${PLUGGY}/v2/transactions\`).href`, que resolve os dois formatos — mesma técnica que o SDK oficial (`pluggy-node`) usa por precaução. **Não assumir que testar um conector garante o comportamento dos outros 4.** Se a Pluggy mudar o contrato de novo, o sintoma é sempre o mesmo padrão: conta sincroniza, transações não (ou só de alguns bancos), erro no `pluggy_sync_log` — sempre olhar `erro` ali antes de suspeitar de outra coisa.

- **Truncamento silencioso de histórico — "Cartão XP Visa Infinite" ficou travado em exatamente 500 transações por meses, sem nenhum erro visível na tela.** Causa raiz: a sincronização histórica completa original dessa conta rodou **antes** do fix do bug de `next` relativo (item acima) — a página 1 (500 linhas, o tamanho fixo de página da Pluggy) foi upsertada com sucesso, e só depois a montagem da URL da página 2 estourou `TypeError: Invalid URL`, jogando a execução pro `catch`. Como as sincronizações seguintes são **incrementais** (buscam só a partir da última transação salva − 30 dias, nunca revisitam o passado), essa lacuna nunca foi reprocessada — 500 continuou parecendo "completo" indefinidamente. Só apareceu porque o número batia exatamente com o tamanho de página; qualquer conta com histórico menor que uma página nunca exibiria esse sintoma mesmo tendo o mesmo bug. Diagnosticado apagando as linhas dessa conta em `pluggy_transacoes` e forçando uma sincronização completa nova: voltou com 551 (as 51 que faltavam iam de 2025-08-02 a 2025-08-29). **Fix estrutural, não só o dado**: o `try/catch` que envolvia a sincronização inteira foi trocado por um `try/catch` por conta — antes, um erro de paginação numa conta abortava o loop e as contas seguintes da lista nem chegavam a ser tentadas naquele run (mesmo padrão do "carregou alguns e outros não" relatado durante o desenvolvimento). Agora cada conta falha isolada, o log grava `status: 'parcial'` com a lista de contas que falharam em `erro`, e as demais contas do mesmo run são processadas normalmente. Continua não havendo verificação automática de que uma conta tem histórico *completo* (ex: comparar contagem contra o campo `total` da primeira página) — se isso for necessário, é trabalho futuro, não coberto por este fix.

- **Sinal de transação no cartão — CONFIRMADO nos 5 conectores: `DEBIT` sempre positivo, `CREDIT` sempre negativo, sem exceção.** Verificado agregando `count(*) filter (where valor > 0)` / `(where valor < 0)` por banco+tipo nas contas mapeadas como cartão — nenhum dos 5 bancos misturou sinal dentro do mesmo `tipo`. Não precisa de normalização na leitura por enquanto; se um conector futuro vier diferente, vai aparecer como `positivos > 0 and negativos > 0` na mesma linha dessa query.

- **`pluggy_sync_log` ficava com `status: null` numa sincronização que na verdade terminava — CORRIGIDO trocando upsert por transação por upsert em lote (uma chamada por página, não por linha).** Causa raiz: ~1.858 round-trips ao Postgres numa invocação só (5 bancos) estourava o tempo de execução da Edge Function antes de alcançar a atualização final do log — não era limitação da plataforma, era o loop. Agora são ~10 chamadas (uma por página).

- **Sincronizações sobrepostas (reload de página, aba duplicada) — guard do lado do servidor, não só o `disabled` do botão.** O botão "Sincronizar agora" já é desabilitado durante a chamada (`btn.disabled` em `sincronizarPluggy()`), mas isso só cobre clique duplo na mesma aba já carregada — reload de página ou aba duplicada durante uma sincronização em andamento não passa por ali, e gerou execuções sobrepostas reais no `pluggy_sync_log` durante o desenvolvimento (inofensivo, já que o `upsert` é idempotente por `pluggy_id`, mas suja o log). Corrigido no servidor: `pluggy-sync` recusa (HTTP 409) iniciar se já existir um log `status IS NULL` (em andamento) dos últimos 5 minutos pra aquele app. A janela de 5 min existe pra uma execução que travou de verdade (crash, deploy no meio) não bloquear sincronizações futuras pra sempre.

- **O contador `atualizadas` do log estava morto desde o início — `count === 1` nunca distingue insert de update.** Um `upsert` sempre "afeta" 1 linha por registro, seja inserindo ou atualizando, então `count === 1 ? criadas++ : atualizadas++` sempre caía no primeiro branch. Todo `pluggy_sync_log` já registrado mostrava `atualizadas: 0`, inclusive em resyncs que claramente reprocessaram dados existentes — não era impreciso, era **enganoso** (afirmava com confiança "tudo foi criado"). Sem o truque de `xmax` (que exigiria um `.select()` extra e não vale o custo aqui), não dá pra separar insert de update barato via PostgREST. Corrigido colapsando num contador só, `processadas` (total inserido + atualizado) — gravado na coluna `criadas` do log por não exigir migration nova; `atualizadas` fica sempre 0 de propósito agora, não por bug. Tela e toast mostram só "N transação(ões) processada(s)".

- **Cartão mapeado não tem coluna de "Diferença" na tela de Sincronização — a comparação não é definível na Fase 1.** O saldo que a Pluggy devolve pra uma conta `CREDIT` é a fatura em ABERTO no momento (inclui compras do ciclo corrente ainda não fechado); a "fatura do mês selecionado" que o app calcula é uma competência FECHADA. São duas grandezas diferentes por definição — a diferença entre elas nunca vai ser zero de forma confiável, sem que nada esteja errado. Mostrar isso como "Diferença" (igual às contas correntes, onde a comparação É válida) ensinaria a ignorar a coluna — que é o produto inteiro da Fase 1 — inclusive pras contas, onde ela é confiável. A tela mostra saldo real + fatura do app lado a lado pra cartão, mas a diferença fica "— comparação não definida".
  **CORREÇÃO (a formulação original estava errada sobre a Fase 2):** dizia que a Fase 2 fecharia a competência "pelo `billForecastDate` que a própria Pluggy fornece" — falso, a cobertura desse campo é desigual entre bancos (verificado agregando por banco): Nubank 100%, XP 99,8% (550/551), Mercado Pago 93,7% (falta 6,3%), C6 85,1% (falta 14,9%), **Inter 0%** (444/444 sem o campo). Não dava pra fechar competência de forma confiável em cima disso pro Inter. **Essa lacuna está fechada de outra forma, não com `billForecastDate`** — ver a entrada sobre o endpoint `/bills` e `billId` logo abaixo. Comparação de verdade pra cartão depende de `pagamentos_fatura` (ver Fatura de cartão) e da Fase 1.6. **Reavaliável após a Fase 1.6**: com a fatura real vinda de `/bills`, a comparação passa a ser definível (fatura fechada contra competência fechada) — a tela ainda não foi alterada, só marcada como candidata a revisão.

- **Debug de dados da Pluggy em chat: só query agregada, nunca linha crua.** `descricao` tem nome real de gente (transferências), `valor`/`saldo` são dinheiro de verdade — nunca pedir nem colar `select *` dessas tabelas numa conversa. As verificações de fuso e sinal acima foram desenhadas assim de propósito (contagens/booleanos por banco, não a transação em si) — é o padrão a seguir pra qualquer verificação futura também.

- **Sobreposição de 30 dias ao buscar transações incrementalmente.** Cada sincronização busca a partir de "última transação salva − 30 dias", não a partir da última data exata. Motivo: transações `PENDING` viram `POSTED` (e o valor pode mudar) dias depois de aparecerem pela primeira vez — sem essa folga, uma transação que mudou de status/valor depois da primeira sincronização nunca seria revisitada. O `upsert` com `onConflict: pluggy_id` faz esse reprocessamento ser barato.

- **`pluggy_contas.conta_nome`/`cartao_nome`/`ignorar` são preservados pelo `upsert`, nunca sobrescritos pela sincronização — OBSERVADO, não só deduzido da teoria do `ON CONFLICT DO UPDATE`.** A Edge Function só envia as colunas que vêm da Pluggy no payload — como o `ON CONFLICT DO UPDATE` só atualiza colunas presentes no payload, o mapeamento manual sobrevive. Na prática: o mapeamento do Nubank (feito na primeira sincronização) sobreviveu a pelo menos 3 resyncs completos depois (XP/Mercado Pago/Inter/C6) sem precisar remapear.

- **`pluggy_transacoes.valor` fica na convenção crua da Pluggy — não normalizar na ingestão.** Sinal pode variar por conector e tipo de conta/cartão; a Fase 1 é só espelho, então qualquer inversão de sinal encontrada num conector específico deve ser **registrada aqui**, não corrigida silenciosamente no `pluggy-sync`. Corrigir na ingestão esconderia informação que a Fase 2 precisa conhecer.

- **Transação apagada na origem (banco) fica órfã em `pluggy_transacoes` até a Fase 1.5 (webhooks).** A sincronização de hoje é só pull incremental — não há como saber que uma transação sumiu do lado do banco sem comparar o conjunto inteiro ou reagir a um webhook de exclusão. Não é um bug a corrigir agora, é uma limitação conhecida da Fase 1.

### Pluggy — direção da Fase 2 (decisão estratégica, ainda não implementada)

Registrado depois da Fase 1 rodar contra os 5 bancos reais e a coluna de diferença mostrar divergências reais entre saldo real e calculado. Isso não é uma tarefa pendente de "revisar o desenho" — é a decisão de projeto que decorre do resultado observado.

- **A Pluggy é a fonte da verdade do realizado.** Não é coexistência com lançamento manual dali em diante. O app passa a ser camada de **planejamento, categorização, caixinhas e repasses** — não de registro do que já aconteceu no banco/cartão.

- **A diferença observada na tela de Sincronização não indicava bug — media a defasagem dos dados manuais, que é exatamente o problema que motivou a integração.** A leitura anterior ("perto de zero = modelo saudável") pressupunha um extrato em dia que nunca existiu de fato. Não tratar divergência real como sinal de erro de código.

- **Staging com aprovação transação-a-transação foi REJEITADO.** Motivo: é a mesma tarefa manual que já não é feita por falta de tempo, só com roupa nova — morreria pelo mesmo motivo, depois de todo o trabalho de construção. Não reintroduzir achando que é "mais cuidadoso".

- **Peças que faltam no modelo pra Fase 2 — anotadas aqui, ainda NÃO implementadas (nenhuma migration criada ainda; a Fase 1.7, abaixo, resolveu o desenho, migration é o próximo passo depois deste registro).**
  - `extrato.origem_dado` (`'manual' | 'pluggy'`) — **só em `extrato`, não em `lancamentos`.** É onde a importação escreve; `Parcelado`/`Fixo` continuam manuais por natureza — a Pluggy não cria recorrência, só reporta transações individuais já ocorridas. Sem `origem_dado`, depois da primeira importação não dá mais pra saber o que veio de onde, nem desfazer.
  - `pluggy_transacoes.transacao_id` — vínculo de volta pra linha do app que aquela transação da Pluggy gerou. **Precisa vir acompanhado de um campo de origem** (`transacao_fonte` ou nome equivalente), porque a linha casada pode viver em `extrato` OU em `lancamentos` (uma parcela/fixo já lançado) — sem isso o vínculo é irresolvível depois (não dá pra saber em qual tabela buscar). **Reusar a convenção que já existe no app** (`_editingTx.fonte`, valores `'extrato'`/`'lancamentos'`/`'transferencias'` — ver `montarLancamentosMes()` e o modal de edição), não inventar uma nova.
  - `conciliacao_faturas` (cartão, competência, decisão, data) — guarda a decisão já tomada por fatura/mês, pra tela de conciliação não perguntar de novo o que já foi resolvido.
  - **Limitação do critério de casamento (valor+data), não só um número corrigido — o falso positivo do XP (ver Fase 1.7) é o exemplo concreto.** Valor+data casa bem, mas não é chave: uma transação parcelada pode coincidir por valor+data com uma linha de `extrato` sem relação real nenhuma (foi o que aconteceu no relatório 1, antes de separar parcelada de à vista). **Consequência se isso rodasse importação de verdade**: a transação real seria dada como "já registrada" (por causa do casamento espúrio) e nunca importada — perda silenciosa, pior que duplicata, porque duplicata pelo menos aparece pra revisão e perda silenciosa não aparece em lugar nenhum. **Regra, não refinamento**: qualquer código de importação futuro que lide com fatura onde há parcelada envolvida **precisa** separar parcelada de à vista antes de casar (via `installmentNumber`/`totalInstallments`, como no relatório 2/3), nunca casar o pool inteiro por valor+data de uma vez.
  - **As duas verificações que estavam planejadas aqui (cobertura de `billForecastDate` + concordância contra `getVencimentoIdx`/`calcularDataVencimento`, e a regra de fallback pra parceladas via `installmentNumber`) foram CANCELADAS, não adiadas.** Motivo: as duas comparariam uma estimativa (`billForecastDate` da Pluggy, ou a inferência do app) contra outra estimativa — na divergência não haveria árbitro pra saber qual acreditar. O endpoint `/bills` (ver abaixo) torna essa aproximação inteira desnecessária: `totalAmount`/`dueDate` vêm do emissor, não são estimados. Substituídas pelas três verificações da Fase 1.6.

- **A Pluggy tem endpoint dedicado de fatura (`GET /bills?accountId=...`) — muda a direção assumida acima de "somar transações + aproximar por `billForecastDate`" para "buscar a fatura real do emissor".** Confirmado via documentação oficial (`docs.pluggy.ai/reference/bills-list`). Devolve por fatura: `id`, `dueDate` (vencimento real, não calculado), `billClosingDate` (fechamento real), `totalAmount`, `minimumPaymentAmount`, `allowsInstallments`, `financeCharges[]` (juros/multa) e `payments[]` (pagamentos já registrados pelo emissor). Isso é estritamente melhor que reconstruir o total somando `pluggy_transacoes` — é o número que o próprio banco/cartão reporta, já líquido de pagamentos. Ver Fase 1.6, abaixo, pro plano de sincronização.
  - **REVERSÃO: `billId` (dentro de `creditCardMetadata`) tratado antes como "detector de erro, não chave de agrupamento" — decisão revertida.** Argumento original: cobertura provavelmente pior que outros campos, e identificador opaco sem contrapartida (nada pra buscar com ele). Os dois caíram: cobertura é 100% nos 5 bancos, inclusive Inter (444/444, mesmo com `billForecastDate` ausente em todas as transações dele) — verificado agregando `jsonb_object_keys(metadata->'creditCardMetadata')` por banco. E com `/bills` existindo, `billId` passa a referenciar uma fatura real (data, total, pagamentos) — deixa de ser opaco, vira chave estrangeira legítima. Registrando a reversão explicitamente pra não parecer que a decisão antiga foi esquecida.
